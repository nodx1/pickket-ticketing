과업지시서 2-2) "피켓 예매 동시 접속 시 병목 구간을 분석하고, Python FastAPI 비동기 루프의 성능을 튜닝한다. Redis 분산 락을 통해 중복 응모를 방지한다."

- 실행일: 2026-11-17
- 도구: `platform/backend/scripts/verify/loadtest_apply.py` (httpx 비동기 — 실제 HTTP 로 실행 중인 API 서버에 부하)
- 환경: 개발 PC 1대(Intel i7-10700K 8코어/16스레드, 128GB) 안에 부하 발생기 · FastAPI(uvicorn) · PostgreSQL 16 + TimescaleDB(Docker) · Redis 7(Docker)를 **함께** 띄움. 운영 서버보다 불리한 조건이다(부하 발생기와 서버·DB 가 CPU 를 나눠 쓴다).
- 결과 원본: `docs/deliverables/evidence/loadtest-apply-*.json`

## 1. 시나리오

| 구분 | 내용 | 통과 조건 |
|---|---|---|
| A. 응모 피크 | 서로 다른 N명이 동시성 C 로 같은 등급에 한 번씩 응모. 사용자마다 다른 클라이언트 IP(X-Forwarded-For) | 오류 0, 응모 행 = N |
| B. 중복 폭주 | D명이 각자 10번씩 동시에 연타(더블클릭·매크로) | 사람당 응모 1행, AP 차감 1회 |

## 2. 처음 측정 — 병목과 결함 발견

동시 300명(동시성 100) 첫 측정에서 **응모 95%가 실패**했다.

| 응답 | 건수 |
|---|---|
| 201 성공 | 15 |
| 500 서버 오류 | 274 |
| 503 | 11 |

원인 두 가지를 로그에서 확인했다.

1. **추첨 풀 중복 생성(기존 결함, 심각)** — `MultipleResultsFound`
   - 첫 응모가 동시에 몰리면 등급당 하나여야 할 추첨 풀이 4개 생겼다.
   - 기존 코드는 Redis 락 안에서 풀을 만들고 `flush` 만 한 채 락을 풀었다. 커밋 전이라 다음 대기자의 재확인 조회에 보이지 않아 각자 풀을 또 만들었다.
   - 풀이 2개 이상이 되면 이후 모든 응모가 `scalar_one_or_none` 에서 500 — **그 등급 추첨이 통째로 멈춘다.**
2. **Redis 연결 고갈** — `MaxConnectionsError: Too many connections`
   - 워커당 연결 상한 50 이 동시 100 요청(속도 제한·분산 락·캐시)에 바로 소진됐고, 상한 도달 시 기다리지 않고 즉시 실패했다.

## 3. 조치

| # | 조치 | 위치 |
|---|---|---|
| 1 | `lottery_pools (event_id, tier_id)` UNIQUE 제약. 이미 중복이 있으면 마이그레이션이 **멈추고 목록을 보여 준다**(자동 병합 금지) | `alembic/versions/gwasup06_1117_lottery_pool_unique.py` |
| 2 | 풀 생성을 SAVEPOINT 안에서 하고, 동시 생성으로 UNIQUE 위반이 나면 되돌린 뒤 커밋된 풀을 다시 읽음 | `lottery_service._apply_inner` |
| 3 | Redis 연결 상한을 설정으로(`REDIS_MAX_CONNECTIONS`, 기본 200), 상한 도달 시 즉시 실패 대신 대기(`BlockingConnectionPool`, `REDIS_POOL_TIMEOUT_SECONDS`=2) | `app/core/redis.py` |
| 4 | 응모의 풀 행 잠금을 배타(FOR UPDATE) → **공유(FOR SHARE)**. 응모끼리는 병렬, 추첨(배타)과는 계속 직렬화 | `LotteryPoolRepository.get_for_share` |
| 5 | 응모 시계열 기록을 트랜잭션 밖(커밋 후 별도 세션)으로 — SAVEPOINT·INSERT·RELEASE 3왕복을 잠금 시간에서 제외 | `timeseries_log.defer_lottery_event` |
| 6 | 기기 공유 신호가 없으면 IP 집계 쿼리 생략(응모당 1왕복) | `sanction_service.check_apply` |
| 7 | 서버 워커 수 확장(uvicorn `--workers`) — Socket.IO 는 Redis 매니저로 워커 간 방송 유지 | 배포 설정 |

## 5. 운영 반영 권고 (이번 범위 밖, 기록용)

- **워커 수**: CPU 코어 수에 맞춰 늘린다(로컬 4워커에서 1.8배). DB 연결 수 = 워커 × (`DB_POOL_SIZE`+`DB_MAX_OVERFLOW`) 를 DB 상한 안에서 잡는다.
- **응모 부수 작업 분리**: 퀘스트 진행·감사 로그 일부를 커밋 후 비동기로 옮기면 잠금 시간이 더 줄어든다.
- **같은 사용자 반복 조회 제거**: 인증·팬 가중치·신규 우대에서 각각 사용자 행을 다시 읽는다 — 요청 범위 캐시로 2왕복 절약 가능.
- **배포 전 확인**: 운영 DB 에 이미 중복 풀이 있으면 gwasup06 마이그레이션이 멈춘다 — 메시지의 목록을 보고 정리 후 재실행.
